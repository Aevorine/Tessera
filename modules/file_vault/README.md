# file_vault

多因素文件加密模块，带 Electron + React + TypeScript（shadcn/ui）图形界面。启动后先进登录页，任意一种方式验证通过才能进入主界面：

- 密码
- 邮箱验证码（需要先在设置里配置好发信邮箱）
- 验证器 App 动态码（Google/Microsoft Authenticator、Authy 等，标准 TOTP）
- **真实指纹**（通过 Windows Hello 调用本机指纹传感器，需要你实际按手指验证；这台电脑没有配置 Windows Hello 时这条路径不可用，设置向导会自动跳过绑定步骤）
- 一次性离线恢复密钥（首次设置时显示一次，请自行妥善保管）

## 使用方法

第一次用之前，先装一次前端依赖（`node_modules/` 没有提交进仓库）：

```bash
cd modules/file_vault/ui
npm install
```

之后每次启动：

```bash
python scripts/run.py run file_vault
```

这条命令实际是在 `ui/` 目录跑 `npm run dev`——会拉起 Vite 开发服务器 + Electron 窗口，Electron 主进程会自动 spawn `backend_server.py` 作为长驻的 Python 后端子进程（通过 stdin/stdout 上的 NDJSON 协议通信），退出窗口时一并结束。

首次运行会自动弹出设置向导（设密码 → 绑定验证器 → [这台电脑支持 Windows Hello 才会有这步] 绑定指纹解锁 → 配置邮箱[可跳过] → 生成并确认保存恢复密钥）。之后每次运行先进登录页，验证通过后进入主界面，选文件、点"加密"或"解密"即可。

### 加密范围 / 批量操作 / 删除源文件

- **加密不区分文件格式**：`container.py` 把任何文件当作原始字节流处理（`open(path, "rb")`，没有任何按扩展名判断的逻辑），txt、mp4、docx、exe……什么格式都一样加密，已经用文本/任意二进制/docx（zip 容器）三种内容实测过。
- **加密和解密都支持一次选多个文件**：文件选择对话框可以多选；单选时和之前一样弹"另存为"精确指定文件名，多选时会让你选一个目标文件夹，每个文件自动按原名 + `.ivault`（解密则还原成原名）保存到那个文件夹里。批量过程中某个文件失败不会中断其余文件，最后会汇总告诉你几个成功几个失败。
- **加密算法可选**：加密时可在界面上三选一——AES-256-GCM（默认，硬件加速）、AES-128-GCM（密钥短一档、略快）、ChaCha20-Poly1305（没有 AES 硬件指令的机器上最快）。三种都是带认证的 AEAD 算法，实测吞吐都在 200–320 MB/s 量级（瓶颈是磁盘不是加密）。选择只影响新加密的文件，算法名记录在 `.ivault` 头部里，解密时自动识别，不用也不能手动选。身份层（IMK 包裹、密钥槽位）始终固定 AES-256-GCM，不受此选择影响。
- **加密文件的头部元数据也是加密的（v2 格式）**：拿到 `.ivault` 文件但没有密钥的人，看不到原始文件名，也无法通过明文 SHA-256 校验值确认"这个加密文件是不是某份已知文件"。这些元数据用文件密钥加密后存在头部（旧的 v1 格式是明文 JSON，会泄露这两项）。v1 老文件仍然可以正常解密和读取，新加密的文件一律写成 v2。
- **"扫描明文残留"功能**：加密（哪怕勾选了安全删除）只处理你选中的那个文件本身，但明文副本往往还在别处——WPS 的自动备份目录（`%APPDATA%\kingsoft\office6\backup` 等）、`~$` 开头的临时文件、`.bak`/`.wbk` 备份、Office 自动恢复文件，以及**磁盘上其它文件夹里的同名副本**（你自己复制过的、或修复工具生成的）。**WPS"文档修复/深度检索"之所以看起来能从加密文件里"恢复"出内容，实际是在全盘搜同名文档副本和它自己的自动备份，跟密文本身无关**——已实测：密文为全随机字节（熵≈8 bits/byte，不含任何明文/ZIP 结构），修复器从密文提取到的数据为零（"包含文件"目录为空），"修复结果"与磁盘上另一处从未加密过的同名原件逐字节相同。因此每次加密完成后会自动扫描以上全部位置（全盘同名搜索为广度优先、限时约 15 秒的尽力而为扫描），界面上列出发现的疑似残留：源目录/编辑器备份里与源文件相关的项默认勾选；"磁盘同名副本"一律**不默认勾选**（里面可能有你要保留的正式原件，防一键误删），由你逐一确认后"安全删除所选"（覆写后删除）。也可以随时点主界面的"扫描明文残留..."按钮，选 `.ivault` 文件来事后检查。
- **默认情况下，加密后原始文件不会被删除**——这是刻意的（避免意外丢数据），但也意味着：如果原始文件本身没有被清理，那么不管加密强度多高、解锁方式设计得多严密，都形同虚设，因为别人根本不需要解锁，直接打开原始文件就行。如果你的目的是保护文件不被别人看到，务必勾选主界面上的"加密后安全删除原始文件"——这个删除是**先用随机字节覆写内容、再删除**（不进回收站，无法通过常规手段恢复），不是普通删除。注意：这是"尽力而为"的安全删除，SSD 的磨损均衡机制理论上仍可能在别处留有底层数据残留，不是对抗专业取证级别的保证，但足以防止别人在系统里直接把原文件打开这种最常见的场景。

### 密码管理

除了文件加密，同一个应用里还有一个"密码管理"页面（主界面点"密码管理"进入，解锁方式跟文件加密完全一样，共用同一个 IMK）：

- 增删改查密码条目（名称/网址/用户名/密码/备注），列表里密码默认打码显示，可以单独切换显示或直接复制。
- 支持导入 Chrome/Edge/Firefox 手动导出的密码 CSV（浏览器"设置→密码管理器→导出密码"生成的那个文件），自动识别列名，Firefox 导出没有"名称"列时用网址域名兜底。导入成功后默认会把那份明文 CSV 安全删除（覆写后删除），避免它躺在磁盘上而使密码管理形同虚设——不想删可以在导入时取消勾选。
- 导出成 Chrome/Edge 兼容的 CSV 格式，可以直接用浏览器自己的"导入密码"功能读取。**不支持导出成 Firefox 专用格式**（Firefox 导入要求额外的 guid/timeCreated 等字段，目前没有实现，这属于有意识的范围裁剪）。

**架构上的一个刻意偏离**：项目约定（见 `modules/README.md`）是"一个模块文件夹 = 一个独立场景，模块间不互相 import"。密码管理功能本应该是一个独立的 `modules/password_vault/`，但用户明确要求"密码管理界面和文件加密界面是同一个应用"，独立模块做不到这一点（除非先把身份系统提升到 `core/`，且两个应用各自维护一个窗口，观感上仍是两个 app）。因此密码管理直接实现在 `modules/file_vault/` 内部（`passwords.py` + `backend_server.py` 里的 RPC + `PasswordScreen.tsx`），复用同一套已解锁的 IMK。这是权衡后的有意选择，不是疏忽。

### 剪贴板历史（六个里程碑全部完成）

跟"密码管理"一样的刻意偏离：剪贴板历史记录功能不是独立模块，而是直接做在 `modules/file_vault/` 里（`clipboard/` 子包），在 Electron 界面里是"剪贴板"标签页，插在"文件"（加密/解密）和"账户"（密码管理）中间，解锁方式复用同一个 IMK——数据库密钥是从 IMK 用 HKDF 派生出来的一把固定密钥，不用你另外记一个剪贴板密码，但也意味着 Vault 锁着的时候剪贴板历史也读不了。完整方案、六个里程碑各自的范围、验收证据、踩过的坑见 `task-progress-clipboard.md`。

功能清单：监听 + SQLCipher 加密入库、自动分类（URL/邮箱/电话/代码/文本）、置顶、搜索/按类型筛选、点击条目复制/尽力自动粘贴到之前的焦点窗口、虚拟滚动（列表很长也不卡）、系统托盘（打开面板/暂停记录/退出）、关闭窗口改为隐藏到托盘不退出、开机自启开关、全局快捷键 Ctrl+Shift+V 呼出面板、应用黑名单（设置页管理，黑名单里的应用复制不记录）、软删除+回收站（7 天后自动清空）、导出/导入 JSON（图片内嵌进文件，换电脑也能带走）、后端进程崩溃后自动重启并要求重新登录。

**关于验证范围要说清楚的**：所有能自动化验证的部分（后端全部 RPC 方法、加密、分类、去重、自我写回抑制、超大内容摘要分支、崩溃自动重启、压力测试）都用脚本实际跑过、贴了真实运行结果，不是口头说测过。但 Electron 图形界面这一层——标签页看起来什么样、点击手感、托盘图标、全局快捷键有没有被别的软件占用——这台开发机的沙盒环境跑不了 Electron 图形界面（缺一个真实的交互式桌面会话），而且我也没有你的 Vault 密码，不会也不该去猜。这部分需要你自己按下面"手动验证清单"里新加的几条走一遍。

独立 CLI 仍然可用，适合不想跑整个 Electron 界面时单独验证监听/入库这一层：

```bash
python -X utf8 modules/file_vault/clipboard/cli.py selftest   # 自动跑 8 条验收场景（用固定测试密钥，不是真 IMK）
python -X utf8 modules/file_vault/clipboard/cli.py listen     # 手动复制点东西，实时看有没有被记录
```

依赖 `sqlcipher3`（SQLCipher 加密数据库）和 `psutil`（读取剪贴板来源应用的进程名），装法见下面的依赖列表。

### 多语言支持

界面支持切换语言（联合国 6 种官方语言：中文/英语/法语/西班牙语/俄语/阿拉伯语），默认跟随操作系统语言，可在任意屏幕右上角手动切换，选择会记住。已知限制：

- git 相关错误信息（如合并冲突时的 `stderr` 原文）、未预期的内部错误详情不翻译，原样展示英文/原始文本。
- 阿拉伯语只做整体从右到左的方向切换，没有逐组件做像素级的 RTL 布局微调。
- 有一部分不常触发的后端调用（详见规格文档 `docs/superpowers/specs/2026-07-10-i18n-language-switch-design.md` 的"已知限制"一节）在失败时界面不会有任何提示，只有开发者控制台可见——这是改动之前就存在的行为，这次多语言支持没有修复它。

### 依赖：Windows Hello 指纹

指纹解锁依赖 `winrt` 包调用 Windows 自己的 Hello API，第一次用之前装一下：

```bash
pip install winrt-Windows.Security.Credentials.UI winrt-Windows.Foundation
```

没有指纹传感器/没配置 Windows Hello 的电脑，这两个包装了也没用——设置向导会自动检测并跳过绑定步骤，不影响其余四种解锁方式。

### 打包成单个 exe

```powershell
cd modules\file_vault\ui
npm run build:standalone
```

产物在 `modules/file_vault/ui/release/<version>/Ideal1 File Vault-Windows-<version>.exe`——单文件便携版，双击就能跑。`build:standalone` 会先编译两个原生 C 助手，再用 PyInstaller 把 Python 后端一起冻结进去，所以**目标电脑不需要装 Python 或 Node**。必须在 Windows x64 上构建（PyInstaller 不是交叉编译器）。完整流程见 [`docs/standalone-exe-release.md`](../../docs/standalone-exe-release.md)。

打包模式**不再写死仓库里的 data 路径**：后端自己走 `data_dir.resolve_data_dir()`，优先 `%LOCALAPPDATA%\Ideal1 File Vault\data`，并在源码树里检测到旧金库时做一次带校验、可重试、不删旧数据的迁移。需要指定别的位置时设环境变量 `IDEAL1_FILE_VAULT_DATA_DIR` 覆盖（跟 `core/config.py` 里 `IDEAL1_` 前缀的约定一致），开发模式同样生效。

## 重要提醒

- **恢复密钥只会显示一次**，设置向导里务必抄写或保存到安全的地方（不要和加密文件放在一起）。如果同时丢失手机（验证器）、这台电脑坏了或重装系统（指纹解锁失效）又忘记密码，恢复密钥是唯一能找回文件的办法——如果连恢复密钥也丢了，文件将无法恢复，这是设计使然，不是 bug。
- 本机身份信息（`data/identity_store.json` + Windows 凭据管理器里的验证器种子/邮箱密钥/SMTP 密码）只对**这台电脑**有效，换电脑不会自动带过去。`data/` 目录已在 `.gitignore` 里排除，不会被提交。
- 邮箱验证码依赖你在设置里填的 SMTP 账号（比如 Gmail/QQ邮箱的"应用专用密码"），没配置之前这条解锁路径不可用。
- 由于是"任意一种方式即可解锁"，整体安全强度取决于最薄弱的那一项——比如密码一旦泄露，其余几道防线形同虚设。如果需要更高安全性（要求多个因素同时满足），需要另外调整设计，当前版本不支持。

## 架构简述

双层信封加密：一个身份主密钥（IMK）在设置时被上述五种方式各自独立包裹一次；每次加密文件时生成一个全新的文件密钥（FK），实际内容用 FK 做分块 AES-256-GCM 加密（快，硬件加速），FK 本身再用 IMK 包一次存进输出文件（`.ivault` 单文件，一进一出，不产生散落的附属文件）。详见各模块内文件顶部的说明：`crypto.py`、`identity.py`、`container.py`。

界面层是 `ui/` 下一个独立的 Electron + React + TypeScript 项目（shadcn/ui 组件库，Nova 预设），不进入 Python 的依赖体系。`backend_server.py` 是唯一的桥梁：一个薄适配层，把 `identity.py`/`container.py`/`totp.py`/`email_otp.py` 的能力包装成 NDJSON 请求/响应/进度协议，本身不含任何加密逻辑。渲染进程通过 `electron/preload.ts` 暴露的 `window.vaultAPI` 调用后端，拿不到裸 Node/文件系统权限（`contextIsolation: true` + `nodeIntegration: false`）。已解锁的 IMK、当前身份数据、进行中的邮箱验证码状态都只存在于 `backend_server.py` 进程内存里，随窗口关闭一起消失。

## 手动验证清单

以下几项无法自动化测试，需要你实际运行一遍确认：

1. `npm install` 之后 `python scripts/run.py run file_vault` 能正常打开窗口，走一遍设置向导、登录页、加密解密一个文件、改设置，确认所有界面都正常。
2. 设置向导里真的按一下指纹传感器完成绑定；重新打开软件，在登录页点"指纹"标签，真的能用指纹解锁。
3. 用手机上真实的验证器 App 扫描设置向导里的二维码，确认扫码绑定、App 显示的验证码真的能通过验证。
4. 在设置向导或"设置"页里填入真实的 SMTP 账号和应用专用密码，点"发送测试邮件"，确认真的能收到邮件。
5. 点"密码管理"进入，走一遍新增/编辑/删除/搜索/显示隐藏密码/复制到剪贴板，确认都正常。
6. 用真实浏览器（Chrome 或 Edge）导出一份密码 CSV，在"密码管理"里导入，确认条目正确、原 CSV 被安全删除；再导出一份 CSV，确认能被浏览器的"导入密码"功能正常读取。
7. 在设置页点"重新绑定指纹解锁"，真的按一下指纹传感器，确认绑定成功；如果之前是旧版本升级上来的身份（指纹槽位是老的机器硬件指纹），确认这一步之后指纹解锁真的能用了。
8. 登录后点"剪贴板"标签页，复制几段文字（普通文字/一个网址/一个邮箱/一段代码）和一张图片，确认列表里实时出现新记录、分类图标符合预期（网址归类到"链接"、邮箱归类到"邮箱"……）；点条目旁边的图钉按钮，确认能置顶/取消置顶，置顶的条目排在最上面。这一项没有在开发环境里跑起来看过——沙盒里跑不了 Electron 图形界面，也没有你的密码解锁真实身份数据，只验证到了后端 RPC 层（见 `task-progress-clipboard.md`），界面这层需要你自己确认一遍。
