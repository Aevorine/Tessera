## 1. 里程碑划分

### M1 —— 协议核心（本机可完整验证）🔨 本次执行

**产出**：`core/` Go 模块 + `cmd/cbnode` 无界面测试节点 + 端到端测试

| 组件 | 内容 |
|---|---|
| `core/identity` | Ed25519 + X25519 身份、device_id、指纹、助记词导出/恢复 |
| `core/crypto` | Noise_IK/XX 封装、SAS 计算、HKDF、BLAKE3 |
| `core/pairing` | QR payload 编解码、一次性令牌、配对状态机、SAS 确认 |
| `core/wire` | 帧编解码、CBOR 消息定义、全部 type |
| `core/discovery` | mDNS 公布与浏览、地址缓存与过期、换网即刷新（子网广播探测留到 M2） |
| `core/transport` | QUIC 拨号/监听、Noise 叠加、流管理 |
| `core/node` | 连接状态机、并行竞速重连、心跳、会话恢复、配对与传输的编排 |
| `core/clipboard` | 多表示模型、HLC、去重、回环抑制、按需拉取 |
| `core/transfer` | 分块、Merkle、位图断点续传、一对多、路径安全 |
| `core/store` | 设备名单与传输断点的持久化（单文件 JSON，原子替换写入） |
| `cmd/tessera-crossdevice` | 命令行节点：可配对、可同步、可传文件；既是测试载体，也是 Windows 端实际随应用启动的后台守护进程 |

> 上表按**实际落地的代码**写。早期草稿里的 `core/session`（已并入 `core/node`）、
> SQLite 存储（实为单文件 JSON）、`cmd/cbnode`（已改名）都已在此更正——
> 文档和代码对不上比没有文档更坑人。

**验收（A1~A8，全部可自动化）**
```
A1 两个 cbnode 通过二维码 payload 完成配对，双方 SAS 一致           → 自动断言
A2 A 复制文本（含 "E = mc²  m/s²  θ̇  ∑∫√"），B 端收到且字节完全相同 → 自动断言
A3 A 复制 2 MB PNG，B 端按需拉取后 BLAKE3 一致                     → 自动断言
A4 传输 200 MB 文件，中途 kill 接收端，重启后从断点续传，最终 Merkle 根一致 → 自动断言
A5 一对三传输同一文件，其中一个接收端故意失败，另外两个仍成功        → 自动断言
A6 连接建立后强制断开，测得重连耗时 < 3 秒（本机回环 < 500 ms）      → 自动断言并打印实测值
A7 路径穿越攻击（"../../../etc/passwd"、"C:\Windows\x"、CON.txt）全部被拒绝 → 自动断言
A8 未配对节点发起连接被拒绝（错误码 UNTRUSTED）                     → 自动断言
```

**M1 实测结果（2026-07-28）**：16 条验收用例全部通过，`go test ./core/... ./test/`。
实测数据：40 MiB 传输 70 MB/s；断开后重连 4~10 ms（目标 <3 s）；中断后只补传缺失分块。

M1 收尾时补掉的两个缺口：

1. **`Connect()` 会把已关闭的会话当成"已连接"返回**。`Session.close()` 只关 `done` 通道，
   把会话摘出 `node.sessions` 的动作在 `run()` 的 defer 里，晚一步。重连循环抢跑到这个窗口
   里就会拿到一具尸体，状态置为 CONNECTED 后 `<-Done()` 立即返回，于是满速空转——UI 一直
   显示"已连接"，实际上谁也连不上。修法是 `Connect()` 与 `newSession()` 都先查 `Alive()`。
   A6 用例同时改成订阅状态事件而不是轮询：本机回环上整个断开→连回来只有 10 ms 上下，
   比轮询间隔还短，靠轮询抓中间态纯看运气，"根本没重连"和"重连快到看不见"长得一模一样。

2. **`core/discovery` 原本没实现**（`zeroconf` 依赖在 go.mod 里但没有任何代码引用），
   候选路径只有缓存地址和历史地址两路。后果是对端一换 IP——换 Wi-Fi、路由器重发 DHCP、
   换网段——两台早就配对过的设备就永远连不上，只能重新扫码。现已补齐并作为第 3 路
   接进竞速，另有 9 条单元测试；真实 mDNS 往返测试默认跳过（设 `TESSERA_MDNS_E2E=1` 开启），
   因为它会往真实局域网发组播，而 CI / 容器 / 严格防火墙下组播被丢弃是常态。

## 3. 全局性能验收目标

> 以下是**开发验收目标**，在"局域网、5 GHz Wi-Fi、设备无重度省电限制"的基准环境下测量。不代表所有网络环境都能达到。

### 配对

| 指标 | 目标 | 测法 |
|---|---|---|
| 二维码识别 → 开始握手 | < 2 s | 埋点计时 |
| 局域网配对全流程完成 | < 15 s（含用户确认 SAS） | 人工计时 |
| 二维码过期后不可用 | 100% | 自动化测试 |
| SAS 不一致时无法完成配对 | 100% | 自动化测试（构造中间人） |

### 剪贴板

| 指标 | 目标 |
|---|---|
| 局域网文本同步中位延迟 | ≤ 300 ms |
| P95 | ≤ 800 ms |
| 图片同步不阻塞 UI | 主线程无 > 16 ms 的阻塞 |
| 同步循环 | 0 次（模糊测试 10000 次复制） |
| 断网期间内容入队并在恢复后送达 | 100% |

### 自动重连

| 指标 | 目标 |
|---|---|
| 同局域网短暂断开后恢复 | 1~3 s（QUIC 迁移场景 < 1 s） |
| 网络切换（Wi-Fi↔5G）后恢复 | < 3 s；传输中的文件不中断 |
| 重连不需要重新扫码 | 100% |
| 重连后未完成文件从断点继续 | 100% |
| 临时设备到期后不再自动重连 | 100% |

### 文件传输

| 指标 | 目标 |
|---|---|
| 单文件大小上限 | > 10 GB（实测 20 GB） |
| 内存占用（传 20 GB） | < 200 MB（绝不整文件读入） |
| 一对多设备数 | ≥ 5（目标 20） |
| 单设备失败不影响其他 | 100% |
| 断点续传正确率 | 100%（Merkle 根一致） |
| 局域网千兆下吞吐 | ≥ 600 Mbps |

### 稳定性

| 指标 | 目标 |
|---|---|
| 进程被杀后任务数据库不损坏 | 100%（模糊测试：随机时刻 kill 1000 次） |
| 重复消息不产生重复文件 | 100% |
| 网络反复切换不产生连接泄漏 | 连接数有上界（fd 监控） |
| 撤销后旧凭据立即失效 | 100% |
| 用户强杀 App 后不显示虚假在线 | 100%（对端 30 s 内标记离线） |
| 连续运行 7 天无内存增长 | RSS 增长 < 10% |

## 4. 测试策略

| 层级 | 手段 |
|---|---|
| 单元测试 | Go `testing`，覆盖率目标 ≥ 75%（crypto/transfer/pairing 要求 ≥ 90%） |
| 属性测试 | `testing/quick`：HLC 排序性质、CRDT 合并幂等性/交换律、bitmap 序列化往返 |
| 模糊测试 | Go `fuzz`：CBOR 解析、帧解析、路径清洗、mDNS TXT 解析 |
| 端到端 | 多个 cbnode 进程互连，脚本驱动 |
| 网络故障注入 | `toxiproxy` 或自研代理：丢包、延迟、抖动、断流、乱序 |
| 混沌测试 | 随机时刻 kill 进程 / 断网 / 切网 / 填满磁盘 |
| 安全测试 | 中间人模拟、重放攻击、路径穿越、超大字段、畸形 CBOR |
| 真机矩阵 | 小米/华为/OPPO/vivo/三星 × Android 10~16，重点测后台存活 |
