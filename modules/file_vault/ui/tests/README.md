# 前端测试：两套并存，各回答一个问题

这个目录里住着两种性质完全不同的测试。它们不互相取代，`vitest.config.ts` 的
`include` 把两者彻底隔开。

| | 静态守卫 | 行为测试 |
|---|---|---|
| 文件 | `tests/*.test.mjs` | `tests/unit/**/*.test.tsx` |
| 跑法 | `npm run test:update` | `npm run test:unit` |
| 运行器 | Node 自带 test runner | vitest + jsdom + Testing Library |
| 手段 | 读 `.tsx` 源码 + 正则断言 | 真的把组件渲染出来点它 |
| 回答 | "那段代码/那条约定还在不在" | "用户这么操作会发生什么" |
| CI | 已接入 | 尚未接入 |

## 为什么保留静态守卫

它们看起来很土，但守的是**渲染测试够不着的东西**——跨文件的约定。比如：

- 每一个 `<StatTile>` 都必须带 `onClick`（数字回答"有多少"，点击回答"是哪些"，
  只答前一半的数字对用户没用）。这条要跨整个 `src/components` 扫，渲染测试
  只能一个组件一个组件地验。
- 正文字号不许低于 16px，含 `text-[10px]` 这类任意值。
- 六种语言的键集合必须一致，且代码里 `t('...')` 用到的键必须真实存在。
- 纯图标控件必须有 Radix Tooltip 而不是 `title=`。

这类"全仓不变量"一旦破了，症状往往是**界面上悄悄少了点什么而没有任何报错**。

## 静态守卫的两个已知弱点

写新守卫时请避开：

1. **钉得比要守的性质还细**，会在无关重构时误报，然后被人一改了之。
   守"顺序"和"存在性"，别把整行源码原文写进正则。
2. **代码搬家就失明**。逻辑从组件挪进 `lib/` 之后，继续盯着原文件只会得到
   "找不到就红"——那不是它要守的性质。守卫要跟着代码走，但**更新之前必须先
   验证不变量本身仍然成立**，不能靠放松断言把红变绿。

空输入判通过是最常见的"守卫看起来全绿其实没在守"的形态，所以扫描类断言都要
先 `assert.ok(checked > 0)`。

## 行为测试怎么写

- **不看 class 名**。用 `getByRole` / `getByLabelText` 定位，断言用户能观察到的
  结果。断言 class 名会让每次样式调整都变成一次测试维护。
- `globals: false`，`describe` / `it` / `expect` 一律从 `'vitest'` 显式 import。
- CSS 当空模块处理，不跑 Tailwind 流水线——断言里没有任何一条依赖计算后的样式。

## 现状

`tests/unit/` 目前是空的：基建先落地，用例分批补。配置里开着
`passWithNoTests: true`，等第一批用例进来之后应当去掉。

优先补的三处（都是既有覆盖为零、且回归代价最高的地方）：
解锁页五个因子的交互、虚拟列表滚动与选中态、以及带持久化的偏好设置在
localStorage 被写入非法值时能否安全回退。
