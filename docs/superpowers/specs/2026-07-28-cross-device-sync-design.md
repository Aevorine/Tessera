# 跨设备剪贴板与文件传输 —— 技术原理与方案

**状态：方案待用户确认，尚未开工**
**日期：2026-07-28**
**范围：Android 手机 / Android 平板 / Windows 桌面三端互通**

---

## 0. 这份文档要解决的问题

用户需求原文拆成 8 条：

1. 手机 ↔ 平板 ↔ 电脑，复制的内容能在另一端直接粘贴；
2. 内容类型覆盖：纯文本、**公式**、**物理符号**、图片；
3. 二维码等方式配对；
4. 跨设备传文件：图片、APK、Word、PDF、txt、exe、Excel、**文件夹**；
5. 一对一 / 一对多传输；
6. 配对时可选**长期**（自己的设备）或**短期**（别人的设备）；
7. Android 端登录方式可选：不登录 / 密码 / 生物识别；
8. **断联后自动重连，且要快**（用户标注为"非常重要"）。

本文档给出每一条的技术原理和落地方案，并明确指出**哪几条在 Android 上有系统级限制**——这类限制不说清楚，做到一半才发现，代价最大。

## 1. 总体架构：本地优先的设备网格，没有服务器

```
        ┌──────────┐        ┌──────────┐        ┌──────────┐
        │  手机     │◄──────►│   平板    │◄──────►│  Windows │
        │ Android  │        │ Android  │        │ Electron │
        └────┬─────┘        └────┬─────┘        └────┬─────┘
             │                   │                   │
             └───────────────────┴───────────────────┘
                    同一套协议（QUIC + Noise），
                    每台设备既是客户端也是服务端
```

**为什么不做中心服务器**：现有产品线的第一承诺是"Nothing leaves your machine"。加一个服务器，等于把这句话作废，还要承担运维、成本和法律责任。局域网内 P2P 在带宽（Wi-Fi 5 GHz 可跑到 30–80 MB/s，远超任何免费云盘）和延迟（<5 ms）上都优于走公网，唯一的代价是"不在同一网络时连不上"——这条用可选的中继兜底（§6.6），默认关闭。

**三层结构**：

| 层 | 职责 | 复用现有代码 |
|---|---|---|
| **协议层**（语言无关规范） | 帧格式、握手、消息类型、错误码 | 新建，是 Android 与桌面之间唯一的契约 |
| **桌面实现** | `modules/link/`（Python）+ Electron UI | 复用 `core/proc.py`、`modules/file_vault/clipboard/*`（分类器、敏感检测、加密历史库）、身份密钥体系 |
| **Android 实现** | 独立 Kotlin 工程 | 全新，但登录/密钥模型照搬桌面金库的信封加密思路 |

## 2. 身份：设备是谁

每台设备首次启动时本地生成一对 **Ed25519** 长期身份密钥：

- 私钥存放位置：Android → Keystore（有 StrongBox 就用 StrongBox）；Windows → 现有金库的加密存储 / Credential Manager。**私钥永不离开设备，永不出现在任何传输中。**
- 设备 ID = 公钥的 SHA-256，取前 8 字节，显示成 `7F2A-9C41-8B03-D5E6` 这种人眼可核对的形式。
- 显示名（"小明的手机"）只是标签，**不参与任何安全判断**。

配对的本质就是：两台设备互相记住对方的公钥，并给这条记录打上信任等级和有效期。

## 3. 配对：把"信物"掰成两半

### 3.1 原理

配对要解决的唯一难题是**中间人攻击**：怎么确认屏幕上这台设备真的是你手里那台，而不是同一 Wi-Fi 下伪装的第三方。密码学上唯一的解法是引入一条**带外信道**（out-of-band）——一条攻击者插不进去的通道。二维码就是最好的带外信道：光学传输，攻击者除非站在你身后拍照，否则拿不到。

### 3.2 六种配对方式（按推荐顺序）

| # | 方式 | 适用 | 安全强度 | 是否需要人工核对 |
|---|---|---|---|---|
| 1 | **扫二维码** | 手机扫电脑/平板屏幕 | 最高（带外） | 否 |
| 2 | **9 位数字码** | 没摄像头 / 摄像头拍不到 | 高（PAKE） | 是（自动校验位） |
| 3 | **同网发现 + 短语核对** | 平板↔电脑，两台都在手边 | 高 | 是（4 个词或 emoji） |
| 4 | **配对链接** | 通过微信/邮件发给别人 | 中（信道不可信） | **强制**核对短语 |
| 5 | **NFC 碰一碰** | 手机↔平板 | 最高（带外） | 否 |
| 6 | **USB / ADB** | 手机↔电脑，完全无网络 | 最高（物理线） | 否 |

### 3.3 二维码里到底放什么

```
ideal://pair?v=1
  &k=<32B Ed25519 公钥, base64url>
  &s=<16B 一次性配对密钥, base64url>     ← 关键
  &n=<显示名>
  &a=<192.168.1.7:8471,10.0.0.3:8471>   ← 当前局域网地址，首次连接直接命中
  &e=<过期时间戳>                         ← 120 秒
```

**为什么二维码里必须带 `s`（一次性密钥），而不是只放公钥**：只放公钥的话，只有扫码方知道对方是谁，被扫方并不知道来连接的是不是刚才扫码的人——认证是单向的。带上一次性密钥后，双方用它做 **Noise_KKpsk0** 握手（或 TLS 1.3 + raw public key + external PSK），认证是双向的，且这个密钥用完即焚、120 秒过期。

握手完成后，双方各自从握手记录（transcript hash）派生一个 6 位短码：`HKDF(handshake_hash, "sas")`。两屏对照一致才落库。二维码路径下这一步可跳过，数字码路径下**强制**。

### 3.4 数字码为什么要用 PAKE

6 位数字只有 100 万种可能，直接当密钥用等于没加密——攻击者抓一次握手包就能离线爆破。**SPAKE2**（或 CPace）这类密码认证密钥交换协议的作用是：把低熵的短码放大成高熵的会话密钥，且攻击者**每猜一次都必须真的连一次**，无法离线爆破。配 3 次失败即销毁，短码就安全了。

### 3.5 长期 / 短期：信任等级

用户要的"自己的设备 vs 别人的设备"，落成三档，每档权限不同：

| 等级 | 显示名 | 有效期 | 剪贴板 | 收文件 | 数据落盘 |
|---|---|---|---|---|---|
| `own` | **我的设备** | 永久 | 双向自动同步 | 免确认直收 | 正常进加密历史库 |
| `trusted` | **信任的人** | 30 天，可续期 | 手动推 / 手动拉，不自动 | 需确认 | 正常 |
| `guest` | **临时设备** | 1 / 8 / 24 小时，到期自动销毁 | **永不同步** | 需确认，逐个 | **不进历史库**，收到的文件进隔离目录 |

三条硬规则：

1. **有效期在两边各自独立判断**，绝不相信对方声称的等级——这是最容易被绕过的地方。
2. `guest` 到期时不是"标记失效"，是**真的把会话密钥和配对记录从密钥环里删掉**。
3. `guest` 会话里的剪贴板内容**永不写入本地数据库**，只在内存里停留。"短期"不只是时间短，更是**不留痕**。

## 4. 发现与自动重连（用户标注"非常重要"的部分）

这一节是整个方案里最值得下功夫的地方。慢的自动重连和没有自动重连，体验上是一回事。

### 4.1 核心思路：永远不依赖单一机制，永远是并发赛跑

绝大多数"自动重连很慢"的产品，问题都出在**每次重连都从头做一遍服务发现**。真实场景里 90% 的重连是"还在同一个 Wi-Fi、刚才息屏了几分钟"，这种情况根本不需要发现。

### 4.2 五条通道，按命中速度排序

| 通道 | 用途 | 典型耗时 | 备注 |
|---|---|---|---|
| **① 热路径：上次地址** | 同网络重连 | **< 200 ms** | 记录每个 peer 最近 3 个可用地址 + 所在网络标识（SSID/网关 MAC），网络没变就直接并发 TCP/QUIC 连过去，300 ms 预算内成功就完全不做发现 |
| **② UDP 广播信标** | 同网换 IP、新设备上线 | 0.5–2 s | 每 2 秒一次（空闲退到 10 秒），比 mDNS 在 Android/Windows 防火墙下更可靠 |
| **③ mDNS / DNS-SD** | 标准发现 | 1–3 s | 服务名 `_ideal._tcp.local`，TXT 带公钥指纹前 4 字节 |
| **④ BLE 广播** | Wi-Fi 关闭、AP 隔离、跨子网 | 2–5 s | **只用来说"我在这、这样找我"，不传数据**；功耗 µA 级，可常开 |
| **⑤ Wi-Fi Direct / Wi-Fi Aware** | 完全没有共同网络 | 5–15 s | Android 侧兜底，桌面侧作接入点 |

三点设计细节：

- **信标不能明文广播设备名**。LocalSend 这类工具直接广播设备名，等于向同一咖啡厅所有人公开你有哪些设备。这里广播的是**轮换假名** `HMAC(配对密钥, 当前时间片)`——只有已配对的设备算得出来并认出你，其他人只看到一串每隔几分钟就变的随机数。
- **信标要签名**，防止有人伪造"我是你的电脑"来骗连接（真正的认证在握手，但签名能让伪造信标在第一步就被丢弃，省掉握手开销）。
- 三条通道**同时跑，谁先成功用谁**，不做串行 fallback。

### 4.3 触发时机：事件驱动，不轮询

固定间隔轮询既慢又费电。真正让重连"快"的是**在状态变化的那一刻立刻动**：

**Windows 侧触发点**
- 网络地址变化（`NotifyAddrChange` / `NetworkStatusChanged`）
- 从睡眠/休眠恢复
- 用户解锁会话
- 应用窗口获得焦点

**Android 侧触发点**
- `ConnectivityManager.NetworkCallback.onAvailable()` —— 连上 Wi-Fi 的瞬间
- 屏幕点亮
- BLE 扫描回调发现已知假名
- 用户打开 App

每个触发点都立刻发起一次"热路径 + 信标"并发扫描。

### 4.4 保活与断线检测

- 长连接上跑 15 秒一次应用层 ping，配 TCP keepalive。
- 3 秒内检测到断线 → **立即重跑热路径**（不退避）。
- 只有冷发现失败才用指数退避（1s → 2s → 4s → … 上限 30s），且退避在收到任何触发事件时立刻清零。

### 4.5 QUIC 带来的额外优势

选 QUIC 而不是裸 TCP，除了多路复用（2 GB 文件传输不会卡住剪贴板同步）之外，两条特性正好命中"重连要快"：

- **0-RTT 会话恢复**：之前连过的 peer，重连时第一个数据包就能带业务数据，不用等握手往返。
- **连接迁移**：手机从 Wi-Fi 切到 5G，连接标识不变，**不需要重新握手**——TCP 在这里必然断线重连。

UDP 被封的环境自动回落 TCP + Noise。

### 4.6 跨网络（可选，默认关闭）

手机在外面用 4G、电脑在家，这时局域网方案必然失效。两条诚实的路子：

1. **UDP 打洞（STUN + 中继兜底）** —— 大部分家用 NAT 能打通，打不通时才走中继。
2. **自建中继** —— 用户自己部署，内容端到端加密，中继只看得到密文和流量大小。

无论哪条都是**用户显式开启**，默认关闭，且开启时明确告知"这一步会有流量经过网络"。

## 5. 剪贴板模型：一个剪贴板项不是一个字符串

### 5.1 原理（这是"公式、物理符号"能不能成的关键）

从 Word 里复制一个公式，Windows 剪贴板里同时放着**至少 5 种表示**：

| 格式 | 内容 | 保真度 |
|---|---|---|
| `MathML` / `OMML` | 公式的语义结构 | 最高，能再编辑 |
| `Rich Text Format` | 带排版的富文本 | 高 |
| `HTML Format` | 网页片段 | 中 |
| `CF_UNICODETEXT` | 退化的纯文本近似 | 低 |
| `CF_DIB` / `PNG` | 渲染出来的图 | 只能看，不能编辑 |

MathType 还会额外放 `LaTeX` 和 `Equation.DSMT4` OLE 对象。

**如果只同步纯文本，公式必然丢失，物理符号会退化成乱码。** 所以协议里的剪贴板项必须是一个**多格式集合**：

```
ClipItem {
  id            : ULID
  origin_device : 设备 ID          ← 防回环用
  clock         : 混合逻辑时钟      ← 冲突判定用，不用墙上时钟
  created_at    : 时间戳
  sensitive     : bool
  flavors: [
    { mime: "application/mathml+xml", size, hash, bytes|blob_ref, rank: 10 },
    { mime: "text/latex",             ...,                        rank: 20 },
    { mime: "text/rtf",               ...,                        rank: 30 },
    { mime: "text/html",              ...,                        rank: 40 },
    { mime: "text/plain;charset=utf-8", ...,                      rank: 90 },
    { mime: "image/png",              ...,                        rank: 95 }
  ]
  preview: { kind: text|image, thumb }
}
```

接收端按**目标应用能吃什么**挑最优格式，排序原则：**语义 > 排版 > 位图**。

### 5.2 各平台的具体做法

**Windows 发送端**
- 用**延迟渲染**（`SetClipboardData(fmt, NULL)` + `WM_RENDERFORMAT`）：40 MB 的图不会在复制那一刻就实体化，只有真的有人粘贴才生成。
- 注册自定义剪贴板格式承载 `MathML` / `text/latex`。

**Windows 接收端**
- 一次性把所有格式都放进剪贴板，让目标应用自己挑——这样粘进 Word 得到公式、粘进记事本得到文本，不需要用户选。

**Android 接收端（→ 手机/平板）**：无限制，前台服务写剪贴板正常工作。

**Android 发送端（手机 → 其他设备）：这里有系统级硬限制，必须说清楚**

自 **Android 10（API 29）** 起，应用**在后台无法读取剪贴板**——`getPrimaryClip()` 返回 null，除非该应用当前有焦点，或者它是**当前默认输入法**。这不是权限问题，是系统行为，无法用申请权限绕过。Android 12 起，任何应用读剪贴板还会弹一个提示条。

因此"手机上随便复制一下，电脑自动就有了"这个体验，在现代 Android 上**没有一个既合规又无感的实现**。四条可选路径，各有代价：

| 路径 | 体验 | 代价 | 建议 |
|---|---|---|---|
| **A. 分享菜单**（`ACTION_SEND` 分享目标） | 复制后点分享 → 选本 App | 多一步操作 | ✅ **主推**，全版本可用，无任何特殊权限 |
| **B. 自带输入法**（IME） | 真正的自动同步 | 用户要切换默认输入法 | ✅ **推荐做成可选组件**，输入法豁免于该限制 |
| **C. 划词菜单**（`ACTION_PROCESS_TEXT`） | 选中文字 → 长按菜单直接发 | 只对文本有效 | ✅ 成本极低，顺手做 |
| **D. 无障碍服务** | 全自动 | Google Play 明确禁止此用途，会被下架 | ⚠️ 仅作为侧载版的高级开关，默认关闭并解释清楚 |

**方案取 A + B + C 组合**：默认装完就能用（A、C），想要全自动的用户可以启用自带输入法（B）。这比"承诺全自动然后做不到"诚实得多。

### 5.3 必须处理的四个细节

1. **回环**：每项带 `origin_device` + 内容哈希，收到的内容写进本地剪贴板时打标记，绝不再广播出去。**这是朴素实现最常见的 bug——两台设备之间无限互相复制。**
2. **冲突**：两端几乎同时复制，用**混合逻辑时钟**判定先后，不用墙上时钟（手机和电脑的时钟本来就有偏差）。
3. **物理符号 / 特殊字符**：统一 NFC 规范化，保留组合符号和变体选择符，全程按**字节 + 声明编码**传输，中途绝不做编解码往返（`½`、`Å`、`⃗` 这类字符就是在往返里丢的）。
4. **大内容**：超过 256 KB 的格式不内联，只传哈希 + 元数据，接收端按需拉取（`own` 设备可预取）。复制一张 50 MB 的图不会卡住同步。

### 5.4 顺手能加的增强（复用现有金库能力）

- **跨设备统一剪贴板历史**：现有 `modules/file_vault/clipboard/` 已经有加密历史库、自动分类、置顶、搜索、按应用黑名单、回收站。同步过来的项直接进这套体系，按内容哈希去重。
- **敏感内容不同步**：复用现有 `sensitive_detector.py`；再加两条——来源应用是密码管理器的不同步、Android 13+ 标了 `EXTRA_IS_SENSITIVE` 的不同步。
- **一次性内容**：可标记"阅后即焚"，接收端粘贴一次后自动清除。

## 6. 文件传输

### 6.1 分块 + 断点续传

- 文件切成 1–4 MB 块，每块算 BLAKE3 哈希，整个文件用 Merkle 根标识。
- 续传 = "我已有 0..N 块，从 N+1 发起"。电梯里断网、切换网络都不用重来。
- 先写 `.part` 临时文件，**整文件哈希校验通过后**才原子改名到位。绝不边收边覆盖目标文件。

### 6.2 文件夹

按**清单（manifest）+ 流**传，不打包成 zip：

```
manifest: [ {相对路径, 大小, 哈希, 是否目录}, ... ]  →  逐个文件的字节流
```

打包成 zip 的问题是要多占一倍磁盘、要等打包完才开始传、且没法断点续传。

**路径必须消毒**（这是文件传输类工具的经典漏洞面，Zip-Slip / 路径穿越）：

- 拒绝 `..`、绝对路径、盘符
- 拒绝 Windows 保留名：`CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9`
- 拒绝结尾的点和空格（Windows 上会被静默去掉，可导致覆盖别的文件）
- 拒绝目标系统的非法字符，限制总路径长度
- 默认拒绝符号链接

### 6.3 一对一 / 一对多

| 场景 | 策略 | 说明 |
|---|---|---|
| 1 对 1 | 单条 QUIC 流 | —— |
| 1 对 ≤4 台 | **并行单播**（默认） | 每个接收端一条独立流，慢的设备不拖累快的 |
| 1 对 >4 台 | **局域网组播 + 前向纠错**（二期） | 发送端只发一份，接收端补拉丢失的块，还能互相补块 |

一期只做并行单播。4 台以内的实际带宽瓶颈在 Wi-Fi 本身，组播的收益不足以覆盖复杂度。

### 6.4 exe / APK 这类可执行文件的安全处理

**这一条不是可选项。** 一个不处理这个问题的文件传输工具，就是一条恶意软件投递管道：

- **Windows 接收**：给收到的文件写上 **Mark-of-the-Web**（`Zone.Identifier` 备用数据流，`ZoneId=3`），让 SmartScreen 和 Office 保护视图照常生效。剥掉 MOTW 等于替攻击者关掉了 Windows 最后一道防线。
- **Android 接收 APK**：只落盘，**绝不静默安装**。安装必须走系统安装器 + 用户点确认（需要 `REQUEST_INSTALL_PACKAGES`）。
- `guest` 等级发来的可执行文件进**隔离目录**，界面上明确标注来源设备和时间。

### 6.5 性能

- 硬件 AES-GCM（Android ARMv8 和 x86 都有指令集支持），不要在移动端用软件实现。
- 大 socket 缓冲区、`sendfile` / `FileChannel.transferTo` 零拷贝。
- 读一次算一次哈希，不重复读盘。
- 目标：5 GHz Wi-Fi 下 **30–80 MB/s**，瓶颈应落在磁盘而非 CPU。

### 6.6 发送体验

一个常驻的"发送托盘"：文件拖进去 → 勾选接收设备 → 排队发送，断线自动续，发完通知。不要求用户在传输过程中盯着界面。

## 7. Android 端登录

三种方式，和桌面金库同一套信封加密思路（每个因子独立包裹同一把主密钥）：

| 方式 | 原理 | 实际保护了什么 |
|---|---|---|
| **不登录** | 数据库密钥存 Keystore，绑定设备 | 防别的 App 读你的数据库文件。**不防拿到你解锁手机的人**——这一点必须在界面上讲明白，不能让用户误以为安全 |
| **密码** | Argon2id（64 MB / t=3 / p=2）派生 + **叠加 Keystore 硬件密钥** | 叠加硬件密钥后，离线爆破必须有这台设备，纯字典攻击失效 |
| **生物识别** | `BiometricPrompt` 授权使用一把 `setUserAuthenticationRequired(true)` 的 Keystore 密钥 | 关键点：指纹**不是"验证通过然后解锁"**，而是**授权使用密钥本身**——所以改包/绕过 App 逻辑没有用，密钥在硬件里 |

两个必须做对的细节：

- `setInvalidatedByBiometricEnrollment(true)`：别人往你手机里加一枚自己的指纹，旧密钥立即作废。
- 生物识别失败要有降级路径（密码），并正确处理各种 `onAuthenticationError` 状态码。

## 8. 传输层与密码学总览

| 项 | 选型 | 理由 |
|---|---|---|
| 传输 | QUIC（回落 TCP） | 多路复用、0-RTT、连接迁移 |
| 握手 | Noise_IK（重连）/ Noise_KKpsk0（配对） | IK 模式重连 1-RTT，已知对方静态公钥 |
| 前向保密 | 每会话临时 X25519 | 长期私钥泄露不解密历史流量 |
| 内容加密 | ChaCha20-Poly1305 / AES-256-GCM | 有硬件 AES 就用 AES，否则 ChaCha |
| 帧格式 | `[u32 长度][u8 类型][CBOR 体]` | CBOR 比 JSON 省、比 protobuf 灵活，二进制友好 |
| 重放防护 | 单调计数器 + 会话 nonce 前缀 | 0-RTT 数据必须有重放防护 |
| 版本协商 | 握手时交换能力集 | 老手机和新电脑仍能互通 |

**0-RTT 的诚实说明**：0-RTT 里第一个包的数据没有前向保密，且理论上可被重放。因此**只允许幂等的小消息走 0-RTT**（如"我上线了"），剪贴板内容和文件传输一律等握手完成。

## 9. 威胁模型（说清楚防什么、不防什么）

**防得住**：
- 同一 Wi-Fi 下的被动窃听、主动中间人
- 未配对设备的连接尝试
- 伪造信标、重放攻击
- 别的 App 读取本地数据库
- 临时设备到期后继续访问

**防不住（且不假装能防）**：
- 已解锁设备的物理接触者（"不登录"模式下尤其）
- 对端设备本身被入侵——配对是双向信任，对方中招了你也会受影响
- 流量分析：同一网络的人看不到内容，但看得到"这两台设备在传大文件"
- 恶意的**已配对**设备发来的恶意文件——MOTW 和隔离目录是缓解，不是免疫

## 11. 需要在实现时逐条核实的平台事实

以下是本方案依赖的、与具体系统版本绑定的行为。写代码前按 `source-driven` 原则查官方文档确认当前版本，不凭记忆写：

- Android 10（API 29）后台剪贴板读取限制及输入法豁免的确切边界
- Android 13（API 33）`ClipDescription.EXTRA_IS_SENSITIVE`、`POST_NOTIFICATIONS` 运行时权限
- Android 12（API 31）蓝牙权限拆分（`BLUETOOTH_SCAN` / `ADVERTISE` / `CONNECT`）
- Android 13（API 33）`NEARBY_WIFI_DEVICES` 替代定位权限
- Android 14（API 34）前台服务必须声明 `foregroundServiceType`（本项目应为 `dataSync` / `connectedDevice`）
- Android `NsdManager` 的已知不稳定行为，是否需要自带 mDNS 实现
- Windows 延迟剪贴板渲染的消息时序、自定义格式注册
- `Zone.Identifier` 备用数据流的写入方式与 SmartScreen 实际行为
