# 独立 EXE 构建与发布

**这份流程必须在 Windows x64 上执行。** PyInstaller 不是交叉编译器——它把当前机器
上的 Python 解释器和已装依赖打进产物，在 Linux 上跑只会得到一个 Linux 可执行文件。

> **一个 release 里只有两个 exe，没有别的。** 没有 `update-manifest.json`，没有
> `update-manifest.sig`，没有 `key-rotations.json`。签名在 exe 里面。
>
> ```
> Tessera.exe          免安装版
> Tessera Setup.exe    安装包
> ```

---

## 零、为什么别的软件"只要一个 exe 就能更新"

这是设计这套东西时最该先想清楚的问题。答案不是"它们不验签"，而是**签名藏在
exe 内部**。

Windows 的 Authenticode 把证书和签名写进 PE 文件里一个专门的数据目录
（`IMAGE_DIRECTORY_ENTRY_SECURITY`），签名覆盖除了这块区域本身之外的全部字节。
于是「分发物」和「它的签名」天然是同一个文件，不可能走散、不可能配错、也不需要
额外上传任何东西。

早先这个项目用的是**外挂签名清单**：把「版本 + 哈希 + 有效期 + Ed25519 签名」
放在 `update-manifest.json` / `.sig` 里，跟 exe 并排发布。密码学强度上它不比
Authenticode 差，甚至多一个 Authenticode 没有的能力（见下面"失去了什么"），代价是
每个 release 三个文件、每次发版都要跑一次离线签名脚本、清单过期还得重签。

换成 Authenticode 之后：

| | 签名清单方案 | 自签名 Authenticode（现在） |
|---|---|---|
| release 里的文件数 | 3（+ 轮换时 4） | **1** |
| 信任根 | 内置的 Ed25519 公钥 | 内置的证书**公钥** SHA-256 |
| 密钥成本 | 免费，自己生成 | **免费，自己生成** |
| 发版动作 | 构建 → 离线签清单 → 传 3 个文件 | 构建（顺带签名）→ 传 1 个文件 |
| 防"回放旧版本" | 有（清单带签名保护的过期时间） | **没有** |
| SmartScreen 首次运行警告 | 有 | 有（只有花钱买 CA 证书才能消掉） |

### 证书要花钱吗——不用

**「签名内嵌进 exe」和「证书要花钱」是两件独立的事**，这一点值得说清楚，因为它是
整个方案能免费落地的原因。

Authenticode 的**格式**不关心证书是谁签发的。`New-SelfSignedCertificate` 造出来的
证书一样能被 signtool 盖进 exe，分发物依然只有一个文件。花钱买 CA 证书买到的其实
只有一样东西：**Windows 默认信任它**。

而"Windows 默认信任"对我们的更新校验不是必需的——我们不需要问 Windows"这个签名者
可信吗"，只需要问"这个签名者是不是我"。后者用一行硬编码的公钥指纹就能回答，而且
**比 CA 模式更强**：

| | CA 证书 | 自签名 + 公钥钉扎 |
|---|---|---|
| 攻击者要冒充你，得 | 骗过某个 CA 拿到同名证书 | **直接拿到你的私钥** |
| 世界上有多少证书能签出 "Valid" | 几十万张 | 一张 |
| 拦住冒充者的是 | 主体名比对 + CA 的身份审核 | 公钥比对 |

所以自签名模式下 Windows 报"根不受信"是**预期结果**，客户端接受这个状态，然后用
公钥比对来定夺。

唯一真正买不到的是 **SmartScreen 信誉**：用户首次运行下载来的 exe 时会看到
"Windows 已保护你的电脑"，需要点「更多信息 → 仍要运行」。这影响首次安装体验，
不影响更新的安全性——应用内更新是我们自己的代码在校验，不经过 SmartScreen。

### 为什么钉公钥而不是证书指纹（Thumbprint）

两个都是硬理由：

- `Thumbprint` 是证书 DER 的 **SHA-1**。SHA-1 的选择前缀碰撞在 2019 年已经被实际
  做出来过（成本约几万美元），而针对证书的碰撞正是那类攻击的经典目标。信任根不该
  建在一个已经被攻破的哈希上。
- 钉**公钥**而不是整张证书，意味着证书过期后可以用**同一对密钥**重新签发一张新
  证书，老客户端照样认。钉整张证书的话，证书一换所有老客户端立刻失去更新能力。

### 失去了什么（如实记录）

**防冻结能力没有了。** 攻击者若能控制你看到的 GitHub 响应，可以一直把某个真实
发布过的旧版本当作 latest 回放给你，把你永远钉在一个已知有漏洞的版本上。所有签名
校验都会通过——因为那确实是我们签的。旧方案靠清单里那个签名保护的 `expiresAt`
识破这种攻击，Authenticode 没有等价物：它证明"这是我们签的"，不证明"这是我们现在
想给你的"。

这是「只发一个 exe」的直接代价，写在这里以免以后有人以为是漏掉了。

## 一、构建（在开发机上）

```powershell
cd <仓库根目录>\modules\file_vault\ui
npm install
npm run build:standalone
```

`build:standalone` 依次做这些事，任一步失败就停：

1. 编译原生 C 助手（`hook_agent.exe`、`fingerprint_verify.exe`）
2. `pyinstaller packaging/file_vault_backend.spec` → `dist/file_vault_backend/`（one-dir）
3. `pyinstaller packaging/file_hook_worker.spec` → `dist/file_hook_worker/`（one-dir）
4. 准备签名证书（不存在就自动创建），核对它和 `signer-policy.json` 钉的公钥一致
5. 签上面两个冻结产物
6. `tsc` + `vite build` + `electron-builder`（两个产物都由 electron-builder 签）
   → `ui/release/0.1.0/Tessera.exe`（免安装版）
   → `ui/release/0.1.0/Tessera Setup.exe`（安装包）

设 `IDEAL1_SKIP_SIGNING=1` 可以完全跳过签名（CI 就是这么用的）。产物照样能跑，
只是更新器会拒绝它。

### 前置依赖

- Python 3.9 + 项目全部运行时依赖（`cryptography` / `pyotp` / `qrcode` / `keyring` /
  `Pillow` / `pywin32` / `sqlcipher3`）
- `pip install pyinstaller`
- MinGW（`gcc`，用于编译两个 C 助手）
- Node 20+（跑 `npm run test:update` 需要 22.6+，它用
  `--experimental-strip-types` 直接加载 .ts）
- Windows SDK 里的 `signtool.exe`（签名用；`IDEAL1_SIGNTOOL` 可指定路径）

### 为什么是两个冻结目标而不是一个

**打包形态按调用频率选，不是全项目统一。** 这是整份设计里最重要的一个判断：

| 目标 | 形态 | 理由 |
|---|---|---|
| `file_vault_backend` | one-file | 整个生命周期只启动一次，那一次解压的成本可接受，换来分发物干净 |
| `file_hook_worker` | one-dir | 被全局快捷键（Ctrl+V / Delete / Shift+Delete）高频拉起，one-file 每次调用都要重新解压几十 MB，延迟不可接受 |

## 二、代码签名 —— 不需要你先做任何准备

**第一次跑 `npm run build:standalone` 时，签名证书会被自动创建。** 没有要先执行的
命令，没有要手工抄写的指纹。

具体发生了什么：

1. 脚本在 `Cert:\CurrentUser\My` 里找一张主体名匹配、带私钥、没过期的代码签名
   证书。找到就直接用（幂等——每次构建都新造一张的话，公钥每次都变，客户端钉的
   那把就永远对不上）。
2. 找不到就自动造一张：RSA-3072 / SHA-256，20 年有效，主体名默认取
   electron-builder 的 `productName`。
3. 自动把私钥备份到 `%LOCALAPPDATA%\Ideal1 Signing\`（绑定当前 Windows 账户，
   不需要密码，所以能无人值守完成）。
4. 把公钥的 SHA-256 写进 `modules/file_vault/ui/signer-policy.json`，并提示你提交。

之后每次构建，脚本都会核对「即将用来签名的证书」和「`signer-policy.json` 里钉的
公钥」是否一致，**不一致直接中断构建**。

### 这个核对挡住的是什么

一个很阴的失败模式：换了台机器构建（或者证书被重建过），脚本用一张新证书签名，
构建成功、上传成功、发布成功、下载下来双击也能跑——**直到已安装的用户点"立即
更新"才发现装不上**。那时候包已经发出去了，而且看不出哪里错了。

有了这个核对，同样的情况会在构建的第三分钟就停下来，并打印出两边的公钥。

### 备份与密钥保护（构建自动完成）

构建脚本自己做完，没有需要手工执行的步骤：

- 私钥以**不可导出**的形式留在 `Cert:\CurrentUser\My`。它仍然能签名，但取不出来
  ——这一条比保护备份文件更要紧：可导出的话，一行
  `$cert.PrivateKey.ExportPkcs8PrivateKey()` 就能把签名身份整个复制走，不弹窗、
  不要口令，攻击者根本用不着去找备份。
- 仓库之外写一份带密码保护的 `.pfx`，密码由 DPAPI 保管（绑定当前 Windows 账户）。

丢了私钥的后果：你再也签不出**已安装客户端**能接受的包——它们钉着旧公钥。唯一
出路是发一个钉新公钥的版本，然后通知用户手动下载一次。

`.pfx` 绝不进仓库（`.gitignore` 里有 `*.pfx` / `*.dpapi` 兜底），绝不进 CI secrets
——任何能改 workflow 的人都能用它签任意东西，这套机制就白做了。

> 备份密码绑定本机，所以它救得了"证书被误删"，救不了"机器报废"。想让备份也挺过
> 后者，双击仓库根的 `secure-signing-key.cmd`，用你自己的口令重新保护它并把存储里
> 那把一并加固。**可选，不做不影响发版。**

### 为什么公钥要提交进仓库，而不是构建时现读

现读的话，换台机器就会静默地改信任根，而 diff 里什么都看不出来。提交进去意味着
「这个构建信任谁」是一个被记录、被审阅、被追踪的决定——改动它必然出现在 code
review 里。

### 什么时候才需要买 CA 证书

只有一个理由：**消掉 SmartScreen 的首次运行警告**，让用户下载后双击就能跑，不用点
「更多信息 → 仍要运行」。

真要买的话（OV 约 $219/年起，EV 约 $290–500，2023 年 6 月起私钥必须存硬件令牌），
把 `signer-policy.json` 的 `publicKeySha256` 清空即可切到 CA 模式：此时要求 Windows
链验证通过且签名带时间戳副署。代码不用改别的。

## 三、发布一个版本

```powershell
cd <仓库根目录>\modules\file_vault\ui

# 1. 改版本号（package.json 的 version 必须和 tag 严格一致）
#    tag 是 v0.1.0，version 就得是 0.1.0

# 2. 构建并签名（证书不存在会自动创建，不需要提前准备）
npm run test:update
npm run build:standalone

# 3. 确认签名真的盖上了（构建脚本不检查这个，你要自己看）
$exe = "release\0.1.0\Tessera-Windows-0.1.0.exe"
Get-AuthenticodeSignature $exe | Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate
```

**自签名证书的 `Status` 会是 `UnknownError`（根不受信），这是正常的。** 要确认的是：

- `SignerCertificate` 存在，且它的 CN 就是 `signer-policy.json` 里的 `publisher`
- 公钥指纹和 `signer-policy.json` 里的 `publicKeySha256` 一致（构建脚本已经核对过
  一遍，这里是发布前的复核）：

```powershell
$cert = (Get-AuthenticodeSignature $exe).SignerCertificate
$sha = [System.Security.Cryptography.SHA256]::Create()
-join ($sha.ComputeHash($cert.GetPublicKey()) | ForEach-Object { $_.ToString('x2') })
```

只有 `Status` 是 `NotSigned` 或 `HashMismatch` 才是真出了问题——客户端把这两种
（以及 `NotSupportedFileFormat` / `Incompatible`）视为致命，其余状态交给公钥定夺。

买了 CA 证书的话则相反：`Status` 必须是 `Valid`，`TimeStamperCertificate` 必须
不为空。

```powershell
# 4. 建 Release，只传这一个文件
gh release create v0.1.0 "$exe" --title "v0.1.0" --notes-file RELEASE_NOTES.md
```

### 客户端对 release 的硬性要求

| 要求 | 不满足会怎样 |
|---|---|
| tag 精确是 `v<严格semver>` | 拒绝。`v0.1.0-beta`、`release-0.1.0` 一律不认 |
| 不是 draft、不是 prerelease | 拒绝 |
| **每种形态有且只有一个 exe** | 缺哪种，那种形态的用户就报"没有对应形态的构建" |
| exe 的签名 CN 与公钥都等于内置的那一份 | 下完之后删掉，报具体原因 |

### 两个 exe 是怎么区分的

**靠文件名里有没有 `Setup` 这个词**，客户端一行代码就能判断
（`electron/updateVersion.ts` 的 `selectUpdateAsset`）。所以
`electron-builder.json5` 里那两个 `artifactName` 改动**必须同步改那边**，两处注释
互相指着对方。

试过也否掉的几种：按文件大小分（两个包大小接近且随版本漂移，脆得没法用）、在
release body 里写清单（body 是仓库侧可控的纯文本，等于把"下哪个"的决定权交给一个
不可信字段）、发两个 release（tag 只有一个，版本比较立刻乱套）。

**同一形态出现两个会直接让那种形态的更新失效**。这是刻意的——手滑把上个版本的
exe 也传上去是很常见的失误，而"随便挑一个"意味着可能悄悄给用户装了个旧版本，并且
表现得完全正常。宁可明确报错。

**缺哪种形态就报错，绝不退而求其次。** 安装版找不到 Setup 包时不会退回去下免安装
版：那会把一个装好的应用替换成游离 exe——注册表项还在、开始菜单快捷方式指向已经
不存在的路径、卸载功能从此失效，而且全程看起来是成功的。

### 时间戳：自签名下不强制，但仍然加

没有时间戳副署的签名会随着签名证书到期而**集体失效**。CA 模式下这是个必然会发生
的定时炸弹（证书最长 460 天），所以客户端**强制**要求副署。

自签名模式下证书有效期是你自己定的（脚本默认 20 年），不存在这个问题，客户端不
强制。但构建脚本仍然会加，因为它把"这个包是什么时候签的"固定下来了——日后排查
"这个 exe 到底是哪次构建出来的"时，这是唯一可靠的线索。

公共时间戳服务只对你提交的摘要签名，不关心你的证书是谁签发的，所以自签名证书一样
能用免费端点。`scripts/build-standalone.mjs` 默认
`http://timestamp.digicert.com`，可以用 `IDEAL1_TIMESTAMP_URL` 换掉。

## 四、证书到期 / 换机器

**换机器**：把 `npm run signing:export` 导出的 `.pfx` 拷过去，双击导入到
`Cert:\CurrentUser\My`，然后正常构建即可——脚本会认出这张证书，核对通过，什么都
不用改。

不导入就直接构建的话，脚本会造一张新证书、发现公钥和仓库里钉的对不上、然后中断，
并打印出两边的值。这正是它该做的。

**证书到期**（默认 20 年后）：用**同一对密钥**重新签发一张证书，代码一行都不用
改——客户端钉的是公钥，不是那张证书。

私钥真的丢了，就没有平滑路径了：

1. 清空 `signer-policy.json` 的两个字段，重新构建（脚本会造新证书并重新钉），
   发一个新版本
2. **已安装的用户升不上去**——他们那个构建里钉的是旧公钥，新包一律拒绝
3. 只能通过 GitHub Releases 页面通知他们手动下载一次

所以那份 `.pfx` 备份是这套机制里最不能丢的东西。

## 四点五、两种形态

| | 免安装版 | 安装包 |
|---|---|---|
| 文件 | `Tessera.exe` | `Tessera Setup.exe` |
| 放哪 | 用户自己决定，U 盘也能跑 | 安装时可选目录，默认当前用户目录 |
| 快捷方式 / 卸载项 | 没有 | 有 |
| 需要管理员权限 | 不需要 | **不需要**（`perMachine: false`） |
| 更新怎么装 | 我们自己的 runner 原地原子替换 | 下新安装包并静默运行它 |
| 更新失败能自动回滚 | **能**（旧 exe 保留成 `.previous-<版本>`） | 不能，由安装程序自己的机制兜 |

**为什么安装包装在用户目录而不是 `Program Files`**：装进 `Program Files` 的话，
每次自动更新都要弹 UAC 提权，否则写不进去。装在用户目录下更新全程无需提权。代价是
同一台机器上别的 Windows 账户看不到这个应用——对一个存私人密码的工具来说，这更像
是特性而不是缺陷。

**卸载不删数据**（`deleteAppDataOnUninstall: false`）。金库、笔记、密码全在
`%LOCALAPPDATA%\Tessera\data` 里，卸载一个应用不该顺手把用户的数据也
带走——想清空的人可以手动删，误卸载的人不该失去一切。

### 为什么安装版的更新不自己替换那个 exe

因为**两种形态在磁盘上根本不是一种东西**。

免安装版就是一个自解压 exe，整个应用都在那一个文件里——替换它 = 更新了全部。
安装版是一整个目录树：

```
...\Programs\Tessera\
    Tessera.exe                     ← 只是 Electron 启动器外壳，几 MB
    resources\app.asar                        ← 真正的应用代码
    resources\backend\file_vault_backend\   ← 冻结的 Python 后端（one-dir），几十 MB
    resources\filehook\...
    *.dll                                     ← Chromium / Electron 的几十个 DLL
    locales\
    Uninstall Tessera.exe
```

只替换那个 exe，换到的仅仅是**外壳**：app.asar 还是旧的、后端还是旧的、DLL 也还是
旧的。而 Electron 二进制和 app 代码是配套的（V8 快照、原生模块 ABI），版本错开
**大概率直接崩**——而且是"更新完就再也打不开"这种最糟的崩法。

整个目录都自己替换当然做得到（electron-updater 就是这么干的），但那要处理运行中被
锁住的 exe 和 DLL、asar 替换、locales……而这套逻辑**安装程序里已经有了**，还经过了
远比我们多的真实环境检验。重写一遍只是重新实现一个安装器。

注册表卸载项、开始菜单和桌面快捷方式跟着更新，是顺带的好处，不是主要理由。

### 安装程序装到哪：原位置

**这不是"另装一份"，是原地升级。** electron-builder 的 NSIS 会把安装路径写进注册表
的卸载项，下次运行时读出来作为默认目标——用户当初选的目录会被沿用。

调用参数三个一个都不能少：

| 参数 | 作用 |
|---|---|
| `/S` | NSIS 的静默安装开关，不弹任何界面 |
| `--force-run` | **静默安装默认不启动应用。** 少了它，用户点完"立即更新"之后应用退出、装完、然后什么都不发生 |
| `--updated` | 告诉新装上的版本"你是被更新上来的" |

`nsis.runAfterFinish` 保持 `true`（默认值）。把它关掉有让 `--force-run` 一起失效的
风险，那正是上面第二行说的那种故障。

### 代价：安装版没有自动回滚

免安装版能回滚是因为旧 exe 就在旁边留着（`.previous-<版本>`）。安装版的回滚要靠
安装程序自己的机制，我们插不上手。这是两条路真实存在的能力差。

## 五、更新在用户侧怎么走

1. 自动检查（默认开，24 小时节流）**只查元数据**，绝不静默下载或替换。开关在
   设置页"更新"区，旁边就是"立即检查"按钮——自动检查关掉之后仍可随时手动查。
2. 用户点「立即更新」→ 下载，边下边限制大小、监控停滞与总时长
3. 下完之后**验 Authenticode 签名**（签名可用 + CN 匹配 + 公钥匹配），验不过
   立刻删掉下载文件并报具体原因
   - 为什么不能像清单方案那样边下边验：Authenticode 覆盖整个 PE 文件，必须拿到
     完整文件才能验。所以下载阶段的大小/停滞限制不承担信任，只做资源保护。
4. **定位"这个应用现在装在哪"**，并在下载之前把能挡的问题都挡掉（见下一节）
5. 主进程**退出之前**把 update runner 复制到
   `%LOCALAPPDATA%\Tessera\updates\runner-<hash>\` 并校验，再启动它
   - 为什么不直接从 resourcesPath 跑：portable 外层启动器会在主进程退出后清理掉
     整个临时 resources 目录，runner 会连同自己的可执行文件一起被删掉
6. runner 等主进程退出 → **再验一次哈希和签名** → 把旧 EXE 保留成 `.previous-<版本>`
   → 原子替换 → 用 `--post-update-health` 启动新版本
7. 新版本在**后端连通、窗口加载完**之后写健康回执
8. runner 等不到回执（120 秒）→ 自动恢复旧 EXE 并重启，失败的新版本保留成
   `.failed-<版本>` 供诊断

「新版本起来了」必须由新版本自己确认，而不是 runner 观察到进程还活着就算数——
一个启动后卡在白屏的版本，进程也是活的。

### 更新之后用户数据（登录信息、密码、金库）保得住吗

**保得住，而且这不是"应该没问题"，是设计上决定的。**

更新动作只碰**一个文件**：那个外层 exe。runner 做的事是把新 exe 原子改名替换掉旧
exe（旧的还保留成 `.previous-<版本>`），此外不动任何东西。

用户的东西全都不在 exe 里：

| 东西 | 存在哪 | 更新时会被碰吗 |
|---|---|---|
| 金库、笔记、剪贴板历史、活动日志 | `%LOCALAPPDATA%\Tessera\data` | 不会 |
| 身份存储（密码/TOTP/恢复码/指纹槽位） | 同上，`identity.json` | 不会 |
| 邮箱与生物识别密钥 | Windows 凭据管理器（keyring） | 不会 |
| 自动检查开关等 UI 偏好 | `userData` 下的 json | 不会 |

**验证方法**：更新完打开应用，用原来的密码登录——不需要重新设置任何东西。万一新
版本起不来，runner 会自动回滚到 `.previous-<版本>`，数据目录同样没被动过。

### 怎么找到"要被替换的那个 exe"

替换动作是不可逆的，所以这一步宁可放弃也不猜。

**首选 `PORTABLE_EXECUTABLE_FILE`** —— electron-builder 的 portable 启动器在拉起
主进程时设的环境变量，指向用户实际双击的那个文件。注意**不能用 `process.execPath`**：
portable 模式下它指向临时解压目录里的 `electron.exe`，替换它毫无意义（下次启动会
重新解压一份）。

**兜底用上次启动记下的路径**。每次启动都往
`%LOCALAPPDATA%\Tessera\install-location.json` 写一次当前位置，所以用户
把 exe 挪了地方之后，这份记录在下一次启动时就跟上了。

但这份记录躺在当前用户可写的目录里，**谁都能往里写一个别的路径**。所以走兜底这条
路时，替换之前必须先验证那个文件确实是我们签的——否则改一行 JSON 就能让更新器把
任意文件覆盖成我们的 exe。用环境变量那条路不需要这一步（它由我们自己的启动器设置）。

两条都拿不到就明确报错让用户手动下载。

### 下载之前先把能挡的问题挡掉

这三项都是"等下完 145MB 才发现"会特别难受的，所以放在下载**之前**：

| 检查 | 挡住的情况 |
|---|---|
| 文件还在吗 | 用户在应用运行期间把 exe 删了或挪走了 |
| 所在目录可写吗 | exe 放在 `C:\Program Files` 下、只读盘上、或被杀毒软件锁住 |
| 空间够吗 | 需要约 2.5 倍包大小 + 200MB：新包、保留的旧包、替换瞬间的两份 |

可写性是**真的创建一个临时文件再删掉**来探测的，不是查权限位。Windows 上能让写入
失败的原因太多（ACL、只读属性、加密盘、被占用），一个个查不完，试一次最可靠。

### 下载落在哪：目标 exe 旁边的一个子目录

`<exe 所在目录>\.ideal1-update\`，成功之后自动删掉。

**必须同卷**，因为 runner 最后那步靠 `rename` 做原子替换，而跨卷的 `rename` 根本不
是原子操作——Node 直接报 `EXDEV`。早先暂存目录固定在 `%LOCALAPPDATA%` 下，对把 exe
放在 D 盘的用户来说，更新会一路走到最后一步才失败：下载、验签全做完了，替换的时候
报错回滚。子目录和父目录必然同卷，这个原子性于是变成**结构上的保证**，而不是碰巧。

**为什么是子目录而不是直接放旁边**：下载文件名就是 release 里的资产名。万一用户把
自己的 exe 改成了跟新资产一模一样的名字，直接放旁边就会在下载过程中覆盖掉**正在
运行的那个 exe**。概率很低，代价不可逆——用一个子目录把这种可能彻底消掉，比论证它
不会发生便宜得多。

### runner 为什么要再验一次签名

哈希只能证明"文件跟主进程当初下的那个一致"，而**期望哈希就写在旁边那份事务 JSON
里**——两个文件都在 `%LOCALAPPDATA%` 下、都是当前用户可写的。能改一个的人就能同时
改另一个。再验一次签名把门槛从"改一行 JSON"抬到"拿出一个由我们的证书签出来的
exe"。这不是万能的（runner 自己也躺在同一个可写目录里），但更新是不可逆动作，值得
多花那几十秒。

## 六、数据目录

打包后不再写死仓库路径，改用 `%LOCALAPPDATA%\Tessera\data`。

首次启动检测到源码树里还有旧金库时会自动迁移一次。迁移按「宁可不迁移，绝不损坏」
设计：

- `IDEAL1_FILE_VAULT_DATA_DIR` 显式指定过就**完全不迁移**
- 跨进程锁，避免两个实例同时搬
- 数据库用 **SQLite backup API** 取一致副本，不裸拷 `.db`（裸拷会漏掉 WAL 里还没
  checkpoint 的事务）
- 写临时目录 → 校验 → 原子改名 → 写完成标记，任一步失败可重来
- **全程不删旧目录**，出任何问题都能手工退回去
- 白名单只搬用户数据，不搬 ~300MB 的 VS Code 模板等开发资产

迁移失败时应用继续用旧目录照常启动——用户不该因为一次搬家失败就打不开自己的金库。

## 七、本机需要跑的验收

自动化能跑的已经跑过了：`npm run test:update`（32 个用例：信任判定 + CSP + 形态
挑选）、`tsc --noEmit`、`npm audit --omit=dev`（0 漏洞）、以及**两种形态的真机
打包**。下面这些只能靠人手在真实 Windows 上验：

**先验这两条**——它们是打包链本身的健康度，之前都出过事故（见
`docs/security-audit-2026-07.md`）：

- [x] `npx electron-builder` 能同时产出 `Tessera.exe`（免安装）和
      `Tessera Setup.exe`（安装包）。**两个目标要分别确认**：安装包那条
      路上的 NSIS 脚本错误完全不会影响免安装版，"构建成功"这四个字曾经只代表
      免安装版成功。

      版本号。出现 `Electron` / `41.x` 说明资源写入被跳过了（`signExecutable` 那条

- [x] `npm run build:standalone` 能出包（含签名那一段）——2026-07-27 真机跑通。

      `UnknownError` 属正常）——2026-07-27 对两种形态都核过，均带 RFC3161 时间戳。
- [ ] 在**没装 Python** 的机器上双击 exe 能登录、读写数据
- [ ] 路径含非 ASCII 字符（如 `D:\我的文档\`）时正常
- [ ] Ctrl+V / Delete / Shift+Delete 全局快捷键生效
- [ ] **重启电脑后**全局快捷键仍然生效（这条最容易踩——验的是 Run 项指向的是
      稳定目录而不是临时 resourcesPath）
- [ ] 旧金库能被迁移到 `%LOCALAPPDATA%`，且旧目录仍在

      这条以前是会失败的
- [ ] **把 exe 放进 `C:\Program Files` 下点更新**，应当在**下载开始之前**就报

- [ ] 更新过程中把 exe 挪走，应当报"应用已经不在启动时的位置了"并回滚
- [ ] **故意上传一个未签名的 exe，客户端下完之后拒绝并显示原因**
